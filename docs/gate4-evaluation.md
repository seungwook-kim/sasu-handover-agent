# 4단계 평가: 인수인계 질문은 나중에 문제가 된 곳을 미리 짚는가

- 날짜: 2026-09-27
- 대상: eGovFrame 공통컴포넌트 전체 기록 (커밋 2,467개)
- 명령: `sasu eval-questions data/repos/egovframe-common-components --at <태그>`

## 결론

사수 질문(지금 고장난 쿼리 제외) 상위 10개의 30%, 상위 50개의 16~20%가 이후 버그 수정이 들어간 메서드를 가리켰다. **무작위(3%)의 5~10배**다. 하지만 **복잡도 높은 순(상위 50개 32~36%)보다는 낮다.** 버그가 날 곳을 맞히는 것만 보면 복잡도가 가장 강한 신호이고, 사수의 가치는 그 자리에 "무엇을 물어야 하는지"를 붙이는 데 있다.

## 방법

1. 과거 태그 시점의 코드를 `git archive`로 꺼내 분석하고 질문을 만든다. 이 시점을 "인수인계 받는 순간"으로 본다.
2. 그 뒤 커밋 중 메시지가 버그 수정인 것(`fix:`, 버그, 오류, 결함, 취약, hotfix)을 고른다.
3. 각 수정 커밋의 **수정 직전 코드**를 파싱해 바뀐 줄이 속한 메서드(`Class.method`)를 모은다. 이것이 정답지다.
4. 질문 상위 K개가 가리키는 메서드 중 정답지에 있는 비율을 잰다. 같은 K개를 복잡도순·영향 범위순·무작위로 골랐을 때와 비교한다.

- 버그 수정 분류에서 "디버그"의 "버그"를 잘못 잡던 문제를 고친 뒤 다시 쟀다 (커밋 수만 조금 줄고 비율은 같음). v4.3.0 행은 고치기 전 값이다.
- 영향 범위순(이 메서드에 닿는 URL 수)은 상위 50개 8%로 약했다. 많이 쓰이는 유틸은 잘 고쳐지지 않는다.
- v4.3.0은 v5.0.0과 코드가 거의 같아(Java 파일 1개 차이) 독립 검증으로 보지 않는다. 검증은 3년 전 코드인 v4.1.0으로 한다.
- "사수 (전체)"가 낮은 이유: 맨 앞에 두는 **끊어진 쿼리**(실행하면 오류가 나는 확인된 고장)는 아직 고쳐지지 않아 정답지에 없다. v4.1.0 시점의 끊어진 쿼리 9개 중 URL에서 이어지는 2개는 3년 뒤인 지금도 그대로다.

## 실험 기록

v5.0.0으로 조정하고 v4.1.0으로 확인했다. 숫자는 상위 10 / 20 / 50개 중 맞힌 수 (당시 "사수 질문 순서" 기준).

| 단계 | 바꾼 것 | 이유 | v5.0.0 | v4.1.0 |
| --- | --- | --- | --- | --- |
| 0 | 처음 규칙 | | 0 / 1 / 6 | (재지 않음) |
| 1 | 우선순위에 복잡도 가중치 `1 + log2(복잡도)` | 종류별로 보니 "복잡한 분기"(19%)와 "드문 값 분기"(25%)가 잘 맞는데, 많이 쓰이는 유틸이 위로 올라옴 | 4 / 4 / 6 | 2 / 4 / 7 |
| 2 | "복잡한 분기" 기본 점수 40 → 70 | 가장 강한 신호가 가장 낮은 점수였음 | 2 / 5 / 6 | 3 / 5 / 7 |
| 3 | 신호 종류가 겹칠수록 +50% | 맞힌 예가 "드문 값 + 복잡도 40"처럼 신호가 겹친 메서드였음 | 3 / 5 / 6 | 3 / 5 / 7 |

## 한계

- "나중에 버그 수정이 들어간 곳 = 인수인계 때 물어봤어야 할 곳"은 완벽한 등식이 아니다. 참고 지표다.
- 버그 수정 여부를 커밋 메시지로 가린다. eGovFrame은 `fix:` 접두어를 꾸준히 써서 비교적 정확하지만 완벽하지 않다.
- 메서드를 `클래스.메서드` 이름으로 맞춘다. 같은 이름의 오버로드는 하나로 본다.
- 한 프로젝트(eGovFrame)로만 쟀다.
- 사람이 답을 받아 두었을 때 실제로 조치 시간이 줄어드는지는 이 평가로 알 수 없다. 사용 테스트 단계에서 본다.
