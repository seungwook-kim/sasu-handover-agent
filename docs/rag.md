# 사수의 RAG 구조와 검색 평가

- 날짜: 2026-09-27 (일상어 평가·재순위·holdout은 2026-10-15)
- 명령: `sasu embed`, `sasu ask`, `sasu eval-search <저장소> --at <태그> --embed local`, `sasu eval-everyday`

## 구조

```
질문 ("휴가 신청할 때 연차가 없으면 어떻게 돼?")
  │
  ├─ 대상 지정이면 (Class.method · URL · 파일:줄) ──────────────┐
  │                                                               │
  └─ 자유 질문이면 검색 (R)                                        │
       BM25 (한국어 글자 2-gram + 카멜 표기 분해)                  │
       + 용어 사전 확장 (VO 필드 주석: 게시물 아이디 → nttId)      │
       + 벡터 검색 (sqlite-vec, 코사인)  ── 선형 결합             │
       + 코드 그래프 전파 (잘 맞는 메서드를 부르는 쪽에 25%)       │
       + LLM 질문 넓히기 + 질문 종류 판정 (LLM이 있으면)           │
       + LLM 재순위: 상위 40 → 6 (Claude API면 기본)               │
                                                                   ▼
근거 수집 (A)  코드 원문 · 이 메서드를 거치는 URL · 부르는 코드와 SQL·테이블
               · Javadoc·주의 주석·수정 이력 · 인수인계 답변 · 커밋 기록(git blame)
               · 인수인계 문서 조각 (넣었으면, 4개까지)
               → 근거마다 번호(E1…)와 등급: 확인된 사실 / 인수인계 답변 / 기록 / 문서
  │
  ▼
생성 (G)  LLM이 근거로만 답한다. 모든 문장은 [사실]/[답변]/[문서]/[추정] + 근거 번호.
          코드가 검사해서 등급과 근거가 안 맞으면 [추정]으로 낮춘다.
          근거로 답할 수 없으면 "모름" + 떠난 개발자에게 물을 질문.
```

- **조각(chunk):** 메서드 하나. 이름(카멜 표기를 쪼갬)·Javadoc·클래스 설명·주석·부르는 메서드 이름·문자열·SQL과 테이블·인수인계 답변을 묶는다 (최대 1,500자). VO getter/setter는 뺀다.
- **임베딩:** `SASU_EMBED_PROVIDER=local`(fastembed, CPU로 한 번) 또는 `api`(OpenAI 호환 `/embeddings`, 현장에서는 사내 임베딩 서버). 조각 글의 해시로 캐시해서 바뀐 조각만 다시 임베딩한다.
- **벡터 저장소:** 분석 결과와 같은 SQLite 파일 안의 sqlite-vec 가상 테이블. 서버가 필요 없다.
- **LLM:** OpenAI 호환 `/chat/completions`(현장: 사내 LLM 서버). 개발 PC에서는 claude CLI나 Claude API(`SASU_LLM_PROVIDER=anthropic`, 넓히기·재순위만 `SASU_EXPAND_PROVIDER=anthropic`)도 쓴다. LLM이 없으면 근거까지만 보여 준다.
- **문서 조각:** 인수인계 문서는 제목 단위 조각으로 따로 검색한다(같은 BM25 + 벡터). 근거 규칙·불일치는 [인수인계 문서](documents.md).

## 검색 평가

**과제:** 버그 증상 설명으로 고칠 메서드를 찾는다.

- 질문: 버그 수정 커밋 제목에서 `fix:`를 뗀 한국어 문장 (예: "개인연차 미등록 사용자의 휴가 신청·수정이 NullPointerException으로 실패하는 문제")
- 정답: 그 커밋이 고친 메서드 (수정 직전 코드 기준)
- 색인은 **수정 전 시점** 코드로 만든다. 커밋 메시지와 수정 뒤 주석이 검색 대상에 섞이지 않게 하려는 것이다.
- v5.0.0(2026-03-30)으로 조정하고, 3년 전 코드인 v4.1.0으로 확인했다.

| 검색 방법 | v5.0.0 R@1 / R@5 / R@10 / MRR (질문 173) | v4.1.0 R@1 / R@5 / R@10 / MRR (질문 171) |
| --- | --- | --- |
| BM25 (글자 2-gram) | 30% / 40% / 51% / 0.352 | 26% / 39% / 50% / 0.330 |
| + 용어 사전 | 29% / 47% / 55% / 0.364 | 26% / 43% / 56% / 0.338 |
| + 그래프 전파 | 28% / 50% / 61% / 0.369 | 26% / 49% / 61% / 0.354 |
| 벡터만 (MiniLM 다국어) | 6% / 13% / 17% / 0.094 | 8% / 12% / 16% / 0.099 |
| BM25 + 벡터 (RRF) + 그래프 | 11% / 36% / 55% / 0.226 | 10% / 36% / 54% / 0.221 |
| **BM25 + 벡터 (선형 결합) + 그래프** | **28% / 53% / 62% / 0.374** | **27% / 49% / 62% / 0.363** |

## 해석

- **효과가 컸던 것은 코드 구조를 쓴 기법이다.** 용어 사전(VO 필드 주석)과 그래프 전파가 Recall@10을 50~51%에서 61%로 올렸다.
- **작은 로컬 임베딩 모델은 혼자서는 약하다 (Recall@10 16~17%).** 일반 문장으로 학습한 모델이라 `insertVcatnManage` 같은 식별자가 많은 조각을 잘 다루지 못한다. 한국어 설명만 담은 조각으로 따로 임베딩해 봐도 비슷했다 (13~14%).
- **섞는 방법이 중요했다.** 순위만 합치는 RRF는 약한 벡터 순위가 BM25의 확신 있는 1순위를 희석해 R@1이 28%에서 11%로 떨어졌다. 점수를 그대로 두고 벡터 코사인을 조금(0.3) 더하는 선형 결합은 손해 없이 두 시점 모두 MRR이 가장 높았다.
- 그래서 기본 검색은 선형 결합 하이브리드로 두고, 코드 검색에 맞는 더 좋은 임베딩(API의 대형·코드 특화 모델)으로 같은 평가를 다시 돌려 볼 자리를 남긴다.

## 실험 기록

| 단계 | 바꾼 것 | 결과 |
| --- | --- | --- |
| 1 | 그래프 전파 50% | R@10은 올랐지만 R@1이 24%로 떨어짐 (컨트롤러가 과하게 올라옴) |
| 2 | 그래프 전파 25% | R@1 28%, R@10 62% 유지. 채택 |
| 3 | 벡터 RRF (같은 비중) | R@1 11%로 떨어짐 |
| 4 | 가중 RRF (벡터 0.3·0.5) | R@1 12~17%, 여전히 손해 |
| 5 | 한국어 설명만 담은 임베딩 조각 | 벡터만 13~14%, 하이브리드도 개선 없음 |
| 6 | 선형 결합 (벡터 0.1~0.3) | 손해 없음. 0.3에서 검증 시점 R@1 26% → 28%. 채택 |
| 7 | 질문 형식 말("어떤·테이블·읽어")을 불용어로 | 두 시점 모두 수치 그대로. "게시글 목록 조회할 때 어떤 테이블을 읽어?"가 주석의 "~ 테이블" 때문에 RSS 메서드로 가던 문제를 없앰 |
| 8 | 말끝 조사·어미 떼기 ("코드는"→코드, "처리해"→처리) | 하이브리드 v5.0.0 28/53/63%·0.374, v4.1.0 27/48/63%·0.359 (전: 28/53/62%·0.374, 27/49/62%·0.363). 평가 질문은 커밋 제목이라 영향이 작고, 말로 묻는 질문에서 "드는·리해" 같은 엉뚱한 2-gram이 사라짐. 명사 끝과 헷갈리는 조사(이·가·의·과·도)는 떼지 않음 |
| 9 | 인수인계 답변과 맞는 메서드 끌어올리기 | 과거 기록 평가에는 사람의 답이 없어 수치 변화 없음. eGovFrame에 답 하나를 넣고 "휴가 신청할 때 09 코드는 왜 따로 처리해?"로 물었을 때 답을 단 메서드가 13위 → 1위 (코드·주석이 긴 메서드 문서에서 답 몇 줄이 BM25 길이 보정에 묻히던 문제) |

## Voyage 임베딩과 재순위 (2026-11-21)

위 실험의 "작은 로컬 임베딩이 약하다"를 API 임베딩으로 다시 쟀다. 질문은 같은 방식(한국어 버그 수정 커밋 제목 → 고친 메서드)이고, 두 번째 프로젝트로 eGovFrame **템플릿** `egovframe-template-simple-backend`(REST API판, Java 199파일 중 공통컴포넌트와 내용이 같은 파일 1개)를 더했다.

- 명령: `sasu eval-search <repo> --at <시점> --embed voyage [--rerank voyage]` (키는 `SASU_EMBED_API_KEY` 또는 `VOYAGE_API_KEY`)
- 임베딩 조각 = BM25 조각 + 원문 코드(최대 4,000자, `SASU_EMBED_CODE=auto`), 질문은 `input_type=query`

**벡터만 R@10 (모델 비교, 템플릿 v4.3.0 56문항, 원문 코드 없이):** MiniLM 39% · voyage-3.5 73% · voyage-code-3 79%. 공통컴포넌트 v5.0.0 175문항: voyage-3.5 83% · voyage-code-3 90%.

**최종 (R@1 / R@5 / R@10 / MRR):**

| 검색 방법 | 템플릿 v4.3.0 (56) | 공통컴포넌트 v5.0.0 (175) |
| --- | --- | --- |
| BM25 + 용어 사전 + 그래프 (임베딩 없음) | 27% / 54% / 64% / 0.378 | 31% / 54% / 62% / 0.401 |
| 벡터만 (voyage-code-3, 원문 코드 포함) | 43% / 75% / 86% / 0.576 | 64% / 89% / 92% / 0.740 |
| 예전 섞기 linear 0.3 (원문 코드 없이) | 29% / 62% / 77% / 0.417 | 32% / 62% / 75% / 0.440 |
| **섞기 minmax 0.8 + 그래프 (새 기본)** | **50% / 80% / 84% / 0.625** | **65% / 89% / 94% / 0.754** |
| 위 + Voyage 재순위 rerank-2.5 | 57% / 75% / 88% / 0.657 | 60% / 83% / 91% / 0.715 |

**해석**

- 점수가 낮았던 가장 큰 이유는 임베딩이었다. 약한 임베딩에 맞춰 정한 섞기(linear 0.3)는 강한 임베딩에서 BM25 1위가 벡터를 덮어써 오히려 벡터만보다 낮았다. 두 점수를 0~1로 맞추고 벡터 쪽 0.8을 두면 두 프로젝트 모두 가장 좋다 (가중치 0.5~0.9는 스크래치 실험에서 R@5 71~77%로 0.7~0.9가 비슷).
- 원문 코드를 임베딩 조각에 붙이면 템플릿 벡터만 R@5 71% → 75%, 섞기 R@5 75% → 80%.
- Voyage 재순위는 스크래치 실험(후보 글 = BM25 조각 + 원문 코드)에서 템플릿 R@5 75% → 80%였지만, 실제 파이프라인(후보 글 = 한 줄 설명 + 원문 코드)으로 다시 재면 템플릿 R@5는 떨어지고 공통컴포넌트는 모든 지표가 떨어졌다. 그래서 `SASU_RERANK=auto`로는 켜지 않는다.
- 템플릿에서 상위 5 밖인 질문 11개 중 5개는 제목에 코드 단서가 없다 ("PR #74 병합에 의한 오류 수정", "GitHub Actions 빌드 실패 대응", 여러 파일을 바꾼 리팩터링). 이를 빼면 R@5는 약 88%다 (빼는 기준은 사람 판단).

**한계:** 질문 수가 작아(56·175) 한 번 실행의 95% 구간이 ±5~12%p다. 섞기 가중치(0.8)는 템플릿 56문항으로 골랐고, 공통컴포넌트는 고른 뒤 확인만 했다. 두 프로젝트 모두 eGovFrame 계열이다. Voyage는 코드를 외부로 보내므로 폐쇄망 현장에서는 쓸 수 없고, 현장의 사내 임베딩 서버로는 다시 재야 한다 (같은 `minmax` 섞기는 `SASU_HYBRID_FUSION=minmax`로 켤 수 있다).

## 일상어 질문 평가 (2026-10-15)

사용성 시험(페르소나 20명)에서 묻기의 가장 큰 실패는 "로그인 5번 틀리면 잠겨?"처럼 **일상어로 물으면 엉뚱한 코드를 대상으로 고르는 것**이었다. 커밋 제목으로 잰 위 평가는 이 문제를 못 잡아서 따로 쟀다.

- 명령: `sasu eval-everyday [--split dev|test|all] [--runs N] [--expand-variant default,strict,union2] [--no-llm] [--out 결과.json]` (분석 파일은 읽기 전용으로 연다. `--runs`면 넓히기 캐시를 읽지도 쓰지도 않는다)
- 평가 세트 `src/sasu/evaluation/everyday.json` (71문항, 정답은 eGovFrame v5.0.0 코드를 읽어 정한 메서드 집합과 근거 한 줄):
  - **dev 19개** = 정답 있는 16(E01~E16) + 코드에 답이 없는 일반 개념 질문 3(G01~G03). 사용성 시험 기록에서 나온 질문이다. 넓히기 가중치 0.7, low_confidence 문턱 12, 넓히기 변형을 모두 이 세트로 정했다.
  - **test 52개** = 정답 있는 44(T01~T44) + 일반 8(H01~H08). 영역을 나눠(uss·uat·sec·ext·sts / cop·sym·dam·utl·ssi·cmm) 새로 쓴 질문이다. 질문을 쓰는 동안 사수 검색을 돌리지 않았고, 측정 전에 확정했으며, 결정에는 쓰지 않고 채점만 했다.
- 지표: 상위 6 후보(묻기 확인 카드에 나오는 수) 안에 정답이 있는 비율, 1위가 정답인 비율, 일반 질문을 `low_confidence`로 표시한 비율, 정답 있는 질문을 잘못 `low_confidence`로 표시한 비율, 질문당 지연.
- 넓히기 LLM(haiku) 출력이 실행마다 달라서 같은 설정을 **캐시 없이 5번** 쟀다. 표의 값은 5번 평균(실행별 최소~최대), 95% 구간은 질문×실행을 합친 Wilson 구간이다. 이 구간은 실행끼리 독립이라고 본 근사라 실제보다 좁다. 한 번 실행만 보면 44문항에서도 구간이 ±12%p 안팎이다(예: 75%면 61~85%).
- 질문별 안정성: 5번 중 항상 맞힘 / 흔들림(1~4번) / 항상 틀림. (a) 대비: 질문마다 5번 중 과반을 맞혔으면 맞음으로 보고 틀림→맞음(+), 맞음→틀림(−)을 셌다.

**LLM 질문 넓히기:** 검색 전에 LLM(claude-code면 haiku, `SASU_EXPAND_MODEL`)이 질문을 코드 말로 넓힌다. 프롬프트에는 코드에서 뽑은 힌트(업무명=클래스 조각 120개 "휴가관리=VcatnManage", 자주 나오는 이름 조각 50개)를 준다. 넓힌 말은 BM25 질의에 가중치 0.7로 더하고(질문 낱말은 1), 벡터 검색은 원래 질문으로 한다. `SASU_QUERY_EXPAND=auto`(기본, LLM이 있으면 켬)·`off`. 실패하면 조용히 지금 검색 그대로, 결과는 `SASU_HOME/cache/query-expand/`에 질문 해시로 둔다. Class.method·URL·파일:줄이 적힌 질문에는 쓰지 않는다.

**low_confidence:** 넓힌 말 없이 질문 낱말만으로 가장 잘 맞는 코드의 BM25 점수가 12보다 낮거나, 1위 후보에 질문 낱말이 하나도 없으면 true. 처음 쓴 "1위 문서에 있는 질문 낱말 비율 < 0.5"는 dev 일반 질문 3/3을 맞혔지만 정답 있는 질문의 81%에도 경고를 띄워서 버렸다 (말끝 "잠겨·지워져"가 코드에 없어 비율이 낮게 나온다).

**low_confidence 2판 (6단계 D, tune 세트 = dev+test 정답 있는 60·일반 11):** 넓히기 LLM이 같은 호출에서 `{"kind": "code"|"general", "terms": [...]}`를 내게 바꿨다 (추가 호출 없음, general이어도 넓힌 말은 받는다). LLM 판정이 있으면 그것만 보고(general이면 경고), LLM이 없거나 실패하면 위 BM25 규칙. 같은 원자료를 LLM 없이 다시 넣어 규칙을 비교했다(`evalset/runs/d-replay.txt`): LLM 판정만 일반 55/55·잘못 경고 10/300(3%), 판정+"1위에 질문 낱말 없음" 17/300(6%), 판정 OR BM25 규칙 27/300(9%), BM25 규칙만 31/55·17/300. 검색 쪽도 함께 고쳤다: LLM이 넓혔으면 필드 주석 용어 사전(당직 → temp 같은 엉뚱한 말이 섞임)을 쓰지 않음, 질문의 동작 말(바꾸·지우·저장·목록…) 중 LLM이 빠뜨린 코드 동사(update·delete·insert·select)를 더함, 상위 30개가 몇 클래스뿐이라 후보가 6개 미만이면 클래스 제한으로 뺀 것으로 채움.

## LLM 재순위 실험 (2026-10-15)

넓히기 뒤에도 **같은 업무의 다른 메서드가 후보를 채우는** 실패(로그인 IP 제한, 당직 목록 등)가 남았다. BM25·벡터는 낱말이 겹치는 메서드를 올릴 뿐 "그 규칙을 실제로 정하는 곳"인지는 모른다. 그래서 검색 상위 후보를 한 줄씩(Class.method · 한글 설명 · 폴더 · URL · 주석 앞 160자 · 부르는 SQL과 테이블 · 부르는 메서드) 빠른 LLM에 보여 주고 질문의 답이 있을 메서드 6개를 고르게 했다 (`rag/rerank.py`).

## holdout 측정

설정(넓히기 프롬프트·가중치·low_confidence 규칙·재순위 풀)을 모두 고른 뒤, **저장소 밖에 두고 그동안 아무도 열지 않은** 질문으로 한 번만 잰 대표 수치다.

- 세트: Java eGovFrame 정답 있는 30 + 일반 6, Python django-oscar 정답 있는 25 + 일반 3. 쓰는 법은 tune 세트와 같다(한국어 일상어, 기존 질문과 뜻이 겹치지 않게, 질문을 쓰는 동안 사수 검색을 돌리지 않음). 세트 파일은 평가에 다시 쓰지 않으려고 저장소에 넣지 않았다.
- 방법: 설정·질문을 바꾸지 않고 재기만 했다. (a) 넓히기 없음 1번, (b) 넓히기만 5번, (c) 넓히기 + 재순위(채택한 기본) 5번. 넓히기는 캐시 없이 5번 받고, 실행 i의 (b)와 (c)는 같은 넓히기 출력을 써서 재순위만의 효과를 짝으로 비교했다. Claude API Haiku 5.5, 재순위 풀 40 · 같은 클래스 3. 명령으로는 `sasu eval-everyday --set <holdout 세트> --split holdout --runs 5 --rerank both`에 해당한다.
- 95% 구간은 둘: 질문×실행을 합친 Wilson 구간(좁게 나옴)과, 평균을 질문 수(30·25)로 본 한 번 실행 구간.

| holdout | 상위 6 평균 (실행별) | 95%: 질문×실행 / 한 번 실행 | 1위 | 항상/흔들/틀림 | (a) 대비 | 지연 |
| --- | --- | --- | --- | --- | --- | --- |
| Java 30문항 (a) 넓히기 없음 | 56.7% | 39~73% / 39~73% | 30.0% | 17/0/13 | - | 0.10초 |
| Java (b) 넓히기 | 68.7% (63~73%) | 61~76% / 52~83% | 30.7% | 19/3/8 | +6 −2 | 1.90초 |
| **Java (c) 넓히기 + 재순위** | **78.0%** (77~83%) | 71~84% / 59~88% | **63.3%** | 22/3/5 | +6 −0 | 3.78초 |
| Python 25문항 (a) 넓히기 없음 | 36.0% | 20~55% / 20~55% | 16.0% | 9/0/16 | - | 0.03초 |
| Python (b) 넓히기 | 79.2% (68~84%) | 71~85% / 61~91% | 31.2% | 15/8/2 | +12 −0 | 1.43초 |
| **Python (c) 넓히기 + 재순위** | **94.4%** (92~96%) | 89~97% / 80~99% | **92.8%** | 23/1/1 | +15 −0 | 3.33초 |

- **대표 수치는 holdout이다:** Java 56.7% → 78.0%, Python 36.0% → 94.4% (상위 6, 5번 평균). 1위 정답은 Java 30.0% → 63.3%, Python 16.0% → 92.8%.
- **tune과의 차이(과적합):** Java (c) tune 97.3% → holdout 78.0% (−19%p), 1위 89.7% → 63.3%. Python (c) 100% → 94.4% (−5.6%p). tune 값은 "설정을 고른 세트"의 기록으로만 쓴다.
- **재순위만의 효과 (c) vs (b), 같은 넓히기 출력:** Java 틀림→맞음 5 · 맞음→틀림 3, Python 3 · 0. Java에서는 (b)가 맞힌 3문항(첨부파일 저장 이름, 사용자 로그 집계 테이블, 명함첩 추가 테이블)을 재순위가 놓쳤다. tune에서는 없던 유형이다.
- **놓친 원인:** 후보 40개 안에 정답이 없음(Java 4문항, Python 1문항 일부), 후보에 있는데 재순위가 고르지 않음(Java 4, Python 1). Java 1문항은 넓히기가 5번 중 2번 일반 질문으로 판정해 잘못 경고했다.
- **일반 질문 경고:** (b)(c) Java 6/6 · Python 3/3 = 100% ((a) Java 16.7%). 정답 있는 질문에 잘못 띄운 경고는 (c) Java 1.3%, Python 0%. **Python (a)는 정답 있는 질문까지 100% 경고했다:** 영어 코드에 한국어 질문이라 질문 낱말의 BM25 점수가 거의 0이어서, LLM 없이 Python 프로젝트를 쓰면 BM25 경고 규칙은 쓸모가 없다.
- 지연은 질문당 검색 + 넓히기 + 재순위 호출 시간이다(Java·Python 넓히기를 동시에 돌림). LLM 호출 593번(넓히기 320, 재순위 273), 입력 약 203만 · 출력 약 9.4만 토큰, 실패 0.
- 정답 확인: Python 정답 메서드 78개는 모두 분석 파일에 있다. Java 120개 중 3개(`EgovUserDetailsHelper`의 짧은 get/is 메서드)는 검색이 getter로 보고 빼지만, 그 질문들에는 다른 정답이 있어 그대로 쟀다.
- **한계:** 정답은 AI가 코드를 읽어 정했다(사람 검수 없음). 프로젝트는 각 1개(eGovFrame 5.0.0, django-oscar 4.2.1), Claude API 한 모델로만 쟀다. 질문 수가 작아 한 번 실행의 95% 구간이 ±12~15%p다.


- 명령: `sasu eval-why --at v5.0.0 --n 15` (LLM: `SASU_LLM_PROVIDER=claude-code`, Sonnet)
- 방법
  1. v5.0.0 이후 버그 수정 커밋 중, 그 커밋이 넣은 줄이 지금도 남아 있는 곳 15개를 고른다.
  2. "이 줄은 왜 이렇게 되어 있나요?"라고 묻는다. 근거에서는 **그 커밋의 메시지를 뺀다** (정답을 숨김).
  3. **사수(RAG):** 코드·호출 관계·주석·다른 커밋 기록을 근거로 [사실]/[답변]/[추정] 형식으로 답한다. **LLM만:** 질문과 그 한 줄만 받는다.
  4. 채점 LLM이 숨긴 커밋 메시지(실제 이유)와 비교해 0/1/2점을 주고, 다른 이유를 추정 표시 없이 단정했는지(환각) 따로 센다.

| 지표 (질문 15개) | 사수 (RAG) | LLM만 |
| --- | --- | --- |
| 평균 점수 (0~2) | **1.0** | 0.27 |
| 이유를 맞힘 (2점) | **7** | 2 |
| 일부라도 맞힘 (1점 이상) | **8** | 2 |
| 틀린 이유를 단정 | **3** | 8 |

- 사수가 맞힌 답은 대부분 **질문한 줄 주변의 코드와 주석**에서 나왔다. 예: `getCurrentDate`는 코드 주석("3-인자 오버로드를 쓰면 항상 IllegalArgumentException")을 근거로 4-인자 호출의 이유를 맞혔고, `EgovMultiLoginPreventor`는 지역변수에 담은 뒤 null 검사를 하는 코드에서 "동시 세션 제거 때 NPE 방지"를 추정했다. LLM만으로는 그 한 줄밖에 볼 수 없다. 이 차이가 검색의 가치다.
- 다른 커밋 메시지로 정답이 새어 들어간 경우는 없었다 (질문별 근거와 답은 `data/out/eval-why.json`).
- 사수가 틀린 이유를 단정한 3건은 "오류 페이지 경로의 error 누락 수정"처럼 **코드만 보면 보안 방어로 보이는** 경우였다. 코드에서 알 수 없는 이유는 사람에게 물어야 한다는 사수의 전제와도 맞는다.

**한계:** 질문이 15개로 적다. 답하는 모델과 채점 모델이 같은 계열(Claude)이라 채점이 한쪽으로 기울 수 있다. 채점이 흔들린 경우도 있었다 (추정으로 표시한 답을 "단정"으로 본 1건). "LLM만"은 일부러 근거를 주지 않은 조건이라, 이 표는 모델 성능이 아니라 **근거를 모아 주는 것의 효과**를 잰 것이다.

## 아직 재지 않은 것

- 더 큰 임베딩 모델(API)로 같은 검색 평가.
- 다른 모델(오픈 웨이트, 사내 서버 배포용)로 같은 답변 평가, 같은 넓히기·재순위 평가.
- 인수인계 문서를 넣은 상태의 "왜?" 답변 평가(문서 근거가 답을 낫게 하는지, [문서] 등급을 잘 지키는지). 문서 검색·불일치는 [인수인계 문서 9절](documents.md#9-평가와-한계)에서 쟀다.
