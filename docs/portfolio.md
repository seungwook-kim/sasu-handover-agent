# 사수 (SASU) 프로젝트 요약

## 한 줄

SI 인수인계에서 **무엇을 물어야 할지 코드 분석으로 먼저 찾고**, 받은 답을 코드 위치에 붙여 두었다가, 새 담당자의 "왜?"에 **근거와 등급을 붙여 답하는** RAG 에이전트.

## 출발점 (직접 겪은 문제)

Java SI 개발 4년 7개월 동안 신규 구축·고도화·유지보수에 투입되며 인수인계는 보통 1주였다. 문서와 말로 설명을 듣지만 **무엇을 물어야 할지 모르는 채로** 기간이 끝나고, 기존 개발자가 떠난 뒤에야 모르는 로직과 버그를 만나 다시 연락하게 된다. 특히 고도화 프로젝트가 가장 힘들었다: 코드는 무엇을 하는지는 보여 주지만 왜 그렇게 했는지는 보여 주지 않는다.

## 만든 것

| 순간 | 기능 |
| --- | --- |
| 투입 첫날 | 프로젝트 지도(기술 스택, 모듈, 여러 모듈이 함께 쓰는 테이블), URL → 메서드 → SQL → 테이블 경로 추적 |
| 인수인계 기간 | 코드만 봐서는 이유를 알 수 없는 곳을 질문으로 생성(끊어진 쿼리, 업무 코드 값 분기, TODO, 저장소 밖 설정 빈 등) → 엑셀 질문지 → 받은 답을 코드 위치에 연결 |
| 떠난 뒤 | "왜?" 질문에 코드·SQL·인수인계 답변·커밋 기록을 근거로 답. 모든 문장에 [사실]/[답변]/[추정]과 근거 번호, 근거가 약하면 코드가 [추정]으로 낮춤. 모르면 떠난 개발자에게 보낼 질문 초안. 일상어 질문은 LLM이 코드 말로 넓혀 찾고, 검색이 고른 코드는 답 전에 사람이 확인 |
| 고도화 전후 | 기존 동작 목록(URL마다 읽고 쓰는 테이블·분기 값) 엑셀 체크리스트, 끊어진 연결·안 쓰는 코드·복사한 코드 |

지원 범위: Java(Spring MVC·Boot, MyBatis·iBatis·JPA·JDBC, JSP·Thymeleaf), Python(FastAPI·Flask·Django). 쓰는 방법: CLI, 웹 화면(위 네 순간을 시작 화면의 단계 카드로 고르고 화면마다 주 버튼 하나, CDN 없음), MCP 서버, Claude Code 플러그인(스킬 + MCP).

## 설계 결정과 이유

| 결정 | 이유 |
| --- | --- |
| 확정할 수 있는 것은 정적 분석으로 (tree-sitter + 정규식) | 호출 관계·SQL·테이블은 LLM이 추측할 일이 아니다. LLM은 모은 근거로 설명만 한다 |
| SQLite + sqlite-vec, 로컬 임베딩은 선택 | 서버 없이 파일 하나. 노트북·보안 환경에서도 가볍게 |
| 검색 = BM25(한국어 글자 2-gram) + 벡터 + 코드 그래프 + 인수인계 답변 | 질문은 한국어, 코드는 영어 식별자. VO 필드 주석으로 용어 사전을 자동으로 만들어 "게시물 번호" → nttId로 넓힌다 |
| 벡터는 RRF가 아니라 선형 결합 | 실험에서 RRF가 약한 벡터 순위로 BM25의 확신 있는 1위를 희석해 Recall@1이 28% → 11%로 떨어졌다 |
| 답변 문장 등급을 코드가 검사 | LLM이 [답변]이라고 해도 인수인계 답변 근거가 없으면 [추정]으로 낮춘다. 답과 코드가 어긋나면 그 점을 짚게 했다 |
| LLM은 OpenAI 호환 주소 하나 | 사내 LLM 서버(키 없는 서버 포함)로 주소만 바꿔 옮긴다 |
| 검색이 고른 코드는 답 전에 사람이 확인 | 사용성 시험(AI 시뮬레이션)에서 일상어 질문에 엉뚱한 코드를 골라, 그 코드에 대한 [사실]이 질문의 답처럼 읽혀 틀린 확신을 만들었다. 근거 검사만으로는 막을 수 없는 실패였다 |
| 일상어 질문은 LLM이 넓히되 BM25에 낮은 가중치로만 | 질문은 "잠겨?", 코드는 `processLoginIncorrect`. 넓힌 말은 실행마다 달라서 질문 낱말이 중심이 되게 했고, LLM이 없으면 원래 검색 그대로 |
| 주석에서 한글 이름표를 뽑되 지어내지 않음 | 업무어("휴가관리")로 찾을 수 있게. 주석에 없으면 비워 둔다 |
| 평가는 공개 프로젝트의 과거 커밋 기록으로 | 사내 코드와 정답지를 쓸 수 없어서, 과거 시점 코드로 질문·검색·답변을 만들고 그 뒤의 실제 수정·커밋 메시지로 채점했다 |

## 결과 (전자정부 표준프레임워크 공통컴포넌트, Java 1,092개 파일)

- URL 1,182개 중 83.3%가 SQL·테이블까지 이어짐 (나머지는 화면만 보여 주는 URL, DB를 쓰지 않는 URL)
- **실제 버그 2건** 발견: Mapper에 없는 쿼리를 부르는 목록 화면, 네임스페이스 오타로 쿼리를 못 찾는 DAO
- 보안 권한 검사를 공통 부모 대신 **47개 컨트롤러에 복사**해 쓰는 곳 발견
- **"왜?" 답변** (커밋 메시지를 숨기고 15문항): 실제 이유를 맞힌 답 사수 7 vs LLM만 2, 틀린 이유를 단정한 답 3 vs 8
- **검색** (버그 수정 커밋 제목 173개로 고칠 메서드 찾기): 상위 10개 안에 정답 63%, MRR 0.374 (BM25만일 때 51%, 0.352에서 용어 사전·코드 그래프·벡터 선형 결합으로 올림)
- **일상어 검색** (사용성 시험에서 나온 질문 16개로 묻기 대상 찾기): 상위 6 후보 안 정답 25% → 69~81%, 1위 정답 13% → 44~50% (LLM 질문 넓히기, 같은 설정 3번의 범위, 질문당 약 +5초). 코드에 답이 없는 일반 질문 3개는 모두 "딱 맞는 코드 없음"으로 경고
- **질문 생성** (과거 시점의 질문 상위 10개가 이후 버그 수정 위치를 가리킨 비율): 30%, 무작위 3%. 다만 복잡도 순과 비슷한 수준이라 "버그 예측"이 아니라 "무엇을 물을지"에 가치가 있다고 정리
- 처음 보는 공개 프로젝트(spring-petclinic, mybatis/jpetstore-6)에 써 보고 오탐·누락 8가지를 고침
- **사용성 시험 (AI 시뮬레이션)**: AI가 신입·주니어 페르소나 20명을 연기해 실제 브라우저로 할 일 60개를 해 본 첫 시험은 성공 58%, 틀렸는데 성공으로 믿은 경우 11건. 묻기 전 대상 확인·한글 이름표·질문 넓히기·단계별 시작 화면을 넣은 뒤 시험한 4명(할 일 16개)은 시작 화면에서 갈 곳을 16번 모두 바로 찾았고 성공 11 · 부분 5 · 실패 0 (할 일이 달라 첫 시험과 나란히 비교하지 않음). 같은 페르소나·같은 할 일로는 게시판 테이블 찾기 7동작 → 3동작, 답 못 받은 질문 건너뛰기 포기 → 성공
- **화면 정리**: 첫 화면 도구 버튼 인수인계 질문 22 → 8, 고도화 준비 14 → 4. 한글 이름표가 eGovFrame URL 1,182개 중 1,153개, 컨트롤러 164개 중 156개에 붙음
- 커밋별 수치와 측정 방법, 고쳤지만 다시 재지 않은 것은 [개선 이력](improvements.md)에 정리
- 테스트 142개, 실제 Claude Code 세션에서 플러그인으로 동작 확인

## 한계 (숨기지 않은 것)

- 사용성 시험은 AI가 페르소나를 연기한 시뮬레이션뿐이다. 실제 신입보다 끈기 있고 꼼꼼할 수 있어 실제 사람(주니어 개발자) 시험이 남았다. 단계별 시험 뒤 고친 곳은 다시 시험하지 않았다.
- 작은 로컬 임베딩 모델은 혼자서는 약하다 (벡터만 Recall@10 17%). 말이 다르면("게시글" vs "게시물") 검색이 흔들린다.
- "왜?" 평가는 15문항이고 답하는 모델과 채점 모델이 같은 계열이다.
- 일상어 검색 평가는 19문항(정답 있는 16 + 일반 3)이고 가중치·문턱을 같은 세트로 정했다. LLM 출력이 실행마다 달라 69~81%로 흔들린다.
