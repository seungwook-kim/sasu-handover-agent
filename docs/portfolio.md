# 사수 (SASU) 프로젝트 요약

## 한 줄

SI 인수인계에서 **무엇을 물어야 할지 코드 분석으로 먼저 찾고**, 받은 답을 코드 위치에 붙여 두었다가, 새 담당자의 "왜?"에 **근거와 등급을 붙여 답하는** RAG 에이전트.

## 출발점 (직접 겪은 문제)

Java SI 개발 4년 7개월 동안 신규 구축·고도화·유지보수에 투입되며 인수인계는 보통 1주였다. 문서와 말로 설명을 듣지만 **무엇을 물어야 할지 모르는 채로** 기간이 끝나고, 기존 개발자가 떠난 뒤에야 모르는 로직과 버그를 만나 다시 연락하게 된다. 특히 고도화 프로젝트가 가장 힘들었다: 코드는 무엇을 하는지는 보여 주지만 왜 그렇게 했는지는 보여 주지 않는다.

## 만든 것

| 순간 | 기능 |
| --- | --- |
| 투입 첫날 | 프로젝트 지도(기술 스택, 모듈, 여러 모듈이 함께 쓰는 테이블), URL → 메서드 → SQL → 테이블 경로 추적 |
| 인수인계 기간 | 코드만 봐서는 이유를 알 수 없는 곳을 질문으로 생성(끊어진 쿼리, 업무 코드 값 분기, TODO, 저장소 밖 설정 빈, Django 시그널·숨은 조회 조건 등) → 엑셀 질문지 → 받은 답을 코드 위치에 연결. 전임자가 남긴 인수인계 문서(docx·xlsx·hwpx·pdf·hwp…)는 비밀을 가려 넣고, 문서와 코드가 다른 곳을 '문서 확인' 질문으로 |
| 떠난 뒤 | "왜?" 질문에 코드·SQL·인수인계 답변·커밋 기록을 근거로 답. 모든 문장에 [사실]/[답변]/[추정]과 근거 번호, 근거가 약하면 코드가 [추정]으로 낮춤. 모르면 떠난 개발자에게 보낼 질문 초안. 일상어 질문은 LLM이 코드 말로 넓히고 후보를 다시 골라(재순위) 찾고, 검색이 고른 코드는 답 전에 사람이 확인. 인수인계 문서는 [문서] 등급으로 코드보다 낮게 인용 |
| 고도화 전후 | 기존 동작 목록(URL마다 읽고 쓰는 테이블·분기 값) 엑셀 체크리스트, 코드·답변·문서를 모아 빈칸만 채우면 되는 인수인계서(docx·md), 끊어진 연결·안 쓰는 코드·복사한 코드 |

지원 범위: Java(Spring MVC·Boot, MyBatis·iBatis·JPA·JDBC, JSP·Thymeleaf), Python(FastAPI·Flask·Django — django-oscar 4.2.1로 확인). 쓰는 방법: CLI, 웹 화면(위 네 순간을 시작 화면의 단계 카드로 고르고 화면마다 주 버튼 하나, CDN 없음), MCP 서버, Claude Code 플러그인(스킬 + MCP).

## 설계 결정과 이유

| 결정 | 이유 |
| --- | --- |
| 확정할 수 있는 것은 정적 분석으로 (tree-sitter + 정규식) | 호출 관계·SQL·테이블은 LLM이 추측할 일이 아니다. LLM은 모은 근거로 설명만 한다 |
| SQLite + sqlite-vec, 로컬 임베딩은 선택 | 서버 없이 파일 하나. 노트북·보안 환경에서도 가볍게 |
| 검색 = BM25(한국어 글자 2-gram) + 벡터 + 코드 그래프 + 인수인계 답변 | 질문은 한국어, 코드는 영어 식별자. VO 필드 주석으로 용어 사전을 자동으로 만들어 "게시물 번호" → nttId로 넓힌다 |
| 벡터는 RRF가 아니라 선형 결합 | 실험에서 RRF가 약한 벡터 순위로 BM25의 확신 있는 1위를 희석해 Recall@1이 28% → 11%로 떨어졌다 |
| 답변 문장 등급을 코드가 검사 | LLM이 [답변]이라고 해도 인수인계 답변 근거가 없으면 [추정]으로 낮춘다. 답과 코드가 어긋나면 그 점을 짚게 했다 |
| LLM은 OpenAI 호환 주소 하나 | 사내 LLM 서버(키 없는 서버 포함)로 주소만 바꿔 옮긴다 |
| 검색이 고른 코드는 답 전에 사람이 확인 | 사용성 시험(AI 시뮬레이션)에서 일상어 질문에 엉뚱한 코드를 골라, 그 코드에 대한 [사실]이 질문의 답처럼 읽혀 틀린 확신을 만들었다. 근거 검사만으로는 막을 수 없는 실패였다 |
| 일상어 질문은 LLM이 넓히되 BM25에 낮은 가중치로만 | 질문은 "잠겨?", 코드는 `processLoginIncorrect`. 넓힌 말은 실행마다 달라서 질문 낱말이 중심이 되게 했고, LLM이 없으면 원래 검색 그대로 |
| 주석에서 한글 이름표를 뽑되 지어내지 않음 | 업무어("휴가관리")로 찾을 수 있게. 주석에 없으면 비워 둔다 |
| LLM 재순위는 넓히기 뒤, 넓은 후보 풀에서 | 넓히기는 정답을 후보 안으로 데려오지만 같은 업무의 다른 메서드가 앞을 채웠다. 상위 40개를 빠른 LLM이 다시 고르게 하자 holdout 상위 6이 Java 68.7% → 78.0%, Python 79.2% → 94.4%. 호출 1번·약 +1.9초라 Claude API일 때만 기본으로 켠다 |
| 설정은 tune으로 고르고 holdout으로 한 번만 잼 | tune에서 Java 97.3%였던 것이 holdout에서 78.0%였다. 고르며 여러 번 본 세트의 수치는 대표 값으로 쓰지 않는다 |
| 인수인계 문서는 [문서] 등급, 원본 없이 비밀을 가린 조각만 | 문서는 오래됐을 수 있어 코드 근거 없이 [사실]이 되지 않게 했다. 인수인계 문서에는 접속 정보가 흔해, 분석 파일을 넘겨도 비밀이 따라가지 않게 |
| 문서–코드 불일치는 규칙 먼저, 값이 안 보이면 다르다고 하지 않음 | 잘못 잡은 불일치는 전임자에게 쓸데없는 질문이 된다. 규칙이 못 보는 설정 값·동작 차이만 선택 LLM 판정으로 |
| 평가는 공개 프로젝트의 과거 커밋 기록으로 | 사내 코드와 정답지를 쓸 수 없어서, 과거 시점 코드로 질문·검색·답변을 만들고 그 뒤의 실제 수정·커밋 메시지로 채점했다 |

## 결과 (전자정부 표준프레임워크 공통컴포넌트, Java 1,092개 파일)

- URL 1,182개 중 83.3%가 SQL·테이블까지 이어짐 (나머지는 화면만 보여 주는 URL, DB를 쓰지 않는 URL)
- **실제 버그 2건** 발견: Mapper에 없는 쿼리를 부르는 목록 화면, 네임스페이스 오타로 쿼리를 못 찾는 DAO
- 보안 권한 검사를 공통 부모 대신 **47개 컨트롤러에 복사**해 쓰는 곳 발견
- **"왜?" 답변** (커밋 메시지를 숨기고 15문항): 실제 이유를 맞힌 답 사수 7 vs LLM만 2, 틀린 이유를 단정한 답 3 vs 8
- **검색** (버그 수정 커밋 제목 173개로 고칠 메서드 찾기): 상위 10개 안에 정답 63%, MRR 0.374 (BM25만일 때 51%, 0.352에서 용어 사전·코드 그래프·벡터 선형 결합으로 올림)
- **일상어 검색** (묻기 대상 찾기, 설정을 고를 때 열지 않은 holdout, 5번 평균): 상위 6 후보 안 정답 Java(eGovFrame 30문항) 56.7% → 78.0%, Python(django-oscar 25문항) 36.0% → 94.4% (LLM 질문 넓히기 + 재순위, Claude API Haiku 5.5), 1위 정답 30.0% → 63.3%, 16.0% → 92.8%. 질문당 약 3.3~3.8초. 설정을 고른 tune 세트에서는 Java 97.3%였어서 19%p가 과적합이었다. 코드에 답이 없는 일반 질문 경고 holdout 9/9, 정답 있는데 잘못 경고 Java 1.3% · Python 0%
- **속도**: 질문 넓히기 5.17초 → 1.46초(claude CLI → Claude API), 웹 묻기 근거 응답 1.49초 → 0.20초(검색 색인 메모리 캐시)
- **Django (django-oscar 4.2.1)**: URL 0 → 161개, URL → 뷰 94.7%, URL → SQL 81.4%, 테이블 65개 중 60개 연결. Django 질문 8가지를 더해 질문 28 → 99개, 상위 20 중 엉뚱한 질문 7 → 2, 정리 후보 URL 오탐 505 → 0. Java 결과는 그대로
- **인수인계 문서** (AI가 만든 가상 문서로 고친 뒤, 새 문서 1개로 확인): 비밀 가림 17/17 (새 문서 5/6), 문서–코드 불일치 재현율 11/12 · 정밀도 11/12 (새 문서 3/6 · 3/3), 문서에만 답이 있는 질문 상위 6 21/22 (새 문서 6/6), 문서를 넣어도 코드 질문 순위 변화 0. 인수인계서 eGovFrame 전체 561쪽 3.3초
- **질문 생성** (과거 시점의 질문 상위 10개가 이후 버그 수정 위치를 가리킨 비율): 30%, 무작위 3%. 다만 복잡도 순과 비슷한 수준이라 "버그 예측"이 아니라 "무엇을 물을지"에 가치가 있다고 정리
- 처음 보는 공개 프로젝트(spring-petclinic, mybatis/jpetstore-6)에 써 보고 오탐·누락 8가지를 고침
- **사용성 시험 (AI 시뮬레이션)**: AI가 신입·주니어 페르소나 20명을 연기해 실제 브라우저로 할 일 60개를 해 본 첫 시험은 성공 58%, 틀렸는데 성공으로 믿은 경우 11건. 묻기 전 대상 확인·한글 이름표·질문 넓히기·단계별 시작 화면을 넣은 뒤 시험한 4명(할 일 16개)은 시작 화면에서 갈 곳을 16번 모두 바로 찾았고 성공 11 · 부분 5 · 실패 0 (할 일이 달라 첫 시험과 나란히 비교하지 않음). 같은 페르소나·같은 할 일로는 게시판 테이블 찾기 7동작 → 3동작, 답 못 받은 질문 건너뛰기 포기 → 성공
- **화면 정리**: 첫 화면 도구 버튼 인수인계 질문 22 → 8, 고도화 준비 14 → 4. 한글 이름표가 eGovFrame URL 1,182개 중 1,153개, 컨트롤러 164개 중 156개에 붙음
- 커밋별 수치와 측정 방법, 고쳤지만 다시 재지 않은 것은 [개선 이력](improvements.md)에 정리
- 테스트 266개, 실제 Claude Code 세션에서 플러그인으로 동작 확인

## 한계 (숨기지 않은 것)

- 사용성 시험은 AI가 페르소나를 연기한 시뮬레이션뿐이다. 실제 신입보다 끈기 있고 꼼꼼할 수 있어 실제 사람(주니어 개발자) 시험이 남았다. 단계별 시험 뒤 고친 곳은 다시 시험하지 않았다.
- 작은 로컬 임베딩 모델은 혼자서는 약하다 (벡터만 Recall@10 17%). 말이 다르면("게시글" vs "게시물") 검색이 흔들린다.
- "왜?" 평가는 15문항이고 답하는 모델과 채점 모델이 같은 계열이다.
- 일상어 검색 평가의 정답은 AI가 코드를 읽어 정했고(사람 검수 없음) eGovFrame·django-oscar 각 1개, Claude API 한 모델로만 쟀다. holdout도 질문 수가 작아 한 번 실행의 95% 구간이 ±12~15%p다. 사내 LLM 서버 모델에서 넓히기·재순위 효과가 같을지는 모른다. LLM 없이 Python 프로젝트를 쓰면 일반 질문 경고(BM25 규칙)가 모든 질문에 떠 쓸모가 없다.
- 인수인계 문서 기능은 실제 SI 문서가 없어 가상 문서로만 쟀고, 새 문서 holdout은 1개뿐이다. 실제 한글·Word로 만든 파일과 한국어 PDF는 시험 전이다. 오프라인 꾸러미에 PDF·HWP 읽기와 Word 출력 의존성을 넣었지만, 꾸러미를 새로 만들어 설치해 보지는 않았다.
